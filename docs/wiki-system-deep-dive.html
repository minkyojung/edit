Wiki 시스템 심화 분석

Karpathy LLM Wiki 패턴(원문 gist) ↔ writer-tauri 현재 구현 매핑.
"Index가 뭐고 위키는 어떻게 만들어지는가" — 그리고 어디가 미완·비효율·사족인가.

0. Karpathy의 원래 그림 — 30초 요약

RAG는 매번 원본을 다시 합성한다. 위키 패턴은 그 반대다 — LLM이 영구적·점증적인 markdown 위키를 유지보수한다. 매번 합성하지 않고, 합성된 결과가 누적된다. "지식베이스 유지의 고된 부분은 읽기·사고가 아니라 bookkeeping이고, LLM은 그걸 잘한다."

3-Layer 구조

Raw Sources

불변. 사람이 큐레이션, LLM은 읽기만.
  • 기사, 논문, 일기
  • 웹 클리퍼, 파일

Wiki Core

가변. LLM이 소유. 사람은 탐색.
  • 요약, 엔티티/개념 페이지
  • index.md (카탈로그)
  • log.md (append-only)

Schema

사람이 편집. LLM 운영 규칙.
  • CLAUDE.md / AGENTS.md
  • 위키 구조, 컨벤션

3가지 동작

동작의미우리 상태
Ingest새 원본 → 위키 갱신 + 로그 기록 (한 소스당 10~15 페이지 터치)구현됨
Query질문 → 위키 검색 → 인용 답변 → 새 사실은 위키로 환류미구현
Lint주기적 헬스체크: 모순, stale, orphan, 지식 공백미구현

1. 우리 구조 매핑 — 페이지 종류로 본 그림

writer-tauri는 모든 문서가 KnownDoc.type prefix로 식별된다. 같은 markdown 파일이지만 누가 쓰느냐로 강하게 구분.

Karpathy우리 (type prefix)역할쓰는 주체
Raw source daily, writing 사용자 메모. ingest의 입력. 사용자만
Wiki page wiki:custom-* 엔티티/개념 페이지. Sarah, Project X, The Pragmatic Programmer. LLM 제안 → 사용자 수락
CLAUDE.md system:conventions LLM에게 주는 운영 규칙. 사용자가 자유롭게 편집. 사용자가 편집
index.md system:index 모든 위키 페이지 한 줄 카탈로그. 시스템이 결정적으로 생성 (LLM 아님)
log.md system:log ingest 패스 1줄씩 append-only 타임라인. LLM이 한 줄 emit
— wiki:profile 사용자 자기소개 페이지. ## Voice / ## About 등 섹션 분리. 별도 파이프라인 + ingest

소스: apps/writer-tauri/src/state/wikiService.ts (라인 30~48에서 type id 정의).

2. Index — 가장 헷갈리는 부분

질문: "system에 인덱스는 뭐고, 위키는 어떻게 만들어지나?"

Karpathy 원본에서 index.md는 LLM이 ingest할 때마다 갱신하는 페이지다 — "이 페이지에 한 줄 요약 추가/수정해줘"라고 시킨다. 우리는 의도적으로 다르다.

우리 index가 하는 일

위키 페이지 전체를 한 줄로 줄인 카탈로그를 결정적으로(자동) 빌드한다. LLM은 안 건드린다. 라인 포맷:

- wiki/Sarah.md [wiki:custom-7n2dvj41] — Sarah: AI팀 PM, 음성 합성 프로젝트 리드 | links: 4
path
파일 경로 (LLM이 read_page 툴에 넘길 키)
[type-id]
verbatim 식별자. LLM이 proposal의 target에 그대로 복사 — 이름·경로보다 안정적
title
Bear/Obsidian 컨벤션: 본문 첫 줄
summary
sidecar .meta.json의 aiSummary → 없으면 본문 둘째 줄 → 없으면 (empty)
links: N
다른 위키에서 이 페이지로 들어오는 [[link]] 개수 (backlink count)

왜 결정적으로? — 기존 LLM-편집 방식의 문제

  • 토큰 비용: 매 ingest마다 index 본문을 다시 쓰면 출력 토큰이 페이지 수에 비례해 늘어남.
  • 드리프트: 모델이 가끔 한 줄 빠뜨리거나 slug를 새로 지어내는 사고. 신뢰성 깨짐.
  • 결정성: knownDocs + sidecar + 본문 backlink는 모두 시스템 메타데이터. 다시 빌드하면 같은 결과.

소스: apps/writer-tauri/src/state/wikiIndex.ts 파일 헤더 코멘트 + buildWikiIndex().

Index가 갱신되는 시점

  위키 페이지 본문 변경 (사용자 편집 / ingest accept)
        │
        ▼
  invalidateWikiIndex()  ──┐
                           │
        cached = null      │  (memory cache 즉시 무효화)
        scheduleWikiIndexPersist() ──┐
                                     │  (200ms debounce)
                                     ▼
                              persistWikiIndexNow()
                                     │
                                     ├─ getWikiIndex()  → buildWikiIndex() 재실행
                                     ├─ writeVaultFile(_system/index.md, content)
                                     └─ Y.Doc 열려 있으면 reloadFromVault

"사용자가 _system/index.md를 직접 편집해도 다음 invalidation에서 덮어쓴다" — 의도된 계약 (시스템이 단일 writer).

3. 위키는 어떻게 만들어지는가 — Ingest 파이프라인

한 줄로: 사용자가 daily에 적은 글 → LLM이 어떤 위키 페이지에 어떤 사실을 추가할지 제안 → 사용자가 수락 → 위키 페이지 끝에 append.

1
트리거 발화 3가지 surface
hooks/useIdleTrigger.ts
(a) 사이드바 Sync 버튼 (명시적), (b) 23:59 단발 타이머, (c) 부팅 시점 어제 데일리 catch-up. 이전엔 "5분 idle 자동 ingest"였지만, 작은 컨텍스트 → 보수 판정 → "no durable content" 로그 쌓임 문제로 폐기됨.
2
Block-hash dedup
agent/ingest/index.ts:185 · lib/blockHash.ts
노트 본문을 blocks로 쪼개 해시 비교. 지난 패스 이후 새로 추가된 block만 LLM에 넘긴다. 같은 패러그래프를 두 번 제안 못 함.
3
Context 조립 — Tier 1/2/3
agent/contextPipeline.ts → assembleContext()
병렬로: Tier 1 = wiki index 스냅샷, Tier 2 = 노트에 [[link]]된 페이지 본문 (hot pages), conventions, self profile.
4
System prompt 어셈블 (cacheable)
agent/ingest/prompts.ts → composeSystemPrompt()
블록 순서: rules + conventions → SELF PROFILE → INDEX → WIKI PAGE 본문들 → 최근 채팅 활동. user prompt는 DATE + NEW NOTE만 — 작고 자주 바뀌어서 캐시 미스 안 만듦.
5
Haiku 호출 + structured tool call
claude-haiku-4-5-20251001 + relayTool submit_ingest_result
모델은 반드시 한 번 툴을 호출. 텍스트 JSON 절대 안 받음 (오염 방지). 툴 input shape: { proposals: [...], logEntry: string | null }.
6
Sanitize + 큐잉
agent/ingest/parse.ts · state/ingestStore.ts
각 proposal은 atomic: { target | suggestNewPage, entity, bullets[], sourceQuote, rationale }. 자유 markdown 금지 (Arc 1 — illegal states unrepresentable). 큐에 들어가 사용자 검토 대기.
7
Banner UI에서 사용자 수락
layout/WikiPageBanner.tsx · IngestProposalCard.tsx
사용자가 해당 wiki 페이지에 진입하면 상단 banner에 "검토할 제안 N건". entity + bullets → ### Entity\n- bullet로 stitch해 페이지 끝에 append. 새 페이지면 createCustomWikiPage(name, body)로 생성.
8
Index 자동 무효화
state/wikiIndex.ts → invalidateWikiIndex()
위키가 변하면 index가 200ms debounce 후 재빌드 + 디스크 쓰기. 다음 ingest는 새 index를 본다.

4. Context Pipeline — LLM이 보는 것

LLM 호출 한 번에 들어가는 것을 3계층으로 나눠 의도적으로 캐시 친화적으로 설계.

  ┌─────────────────────────── system prompt (cacheable prefix) ──────────────────────────┐
  │                                                                                       │
  │  1. SYSTEM_PROMPT_STATIC + conventions  ←  운영 규칙 + 사용자가 편집한 schema          │
  │  2. SELF PROFILE                        ←  wiki:profile 본문                          │
  │  3. INDEX (Tier 1)                      ←  wiki:* 모든 페이지 한 줄 카탈로그          │
  │  4. WIKI PAGE 본문들 (Tier 2)            ←  [[link]] 된 페이지만 풀바디 (30K char budget)│
  │  5. TODAY'S CHAT ACTIVITY (선택적)        ←  지난 ingest 이후 채팅 thread 요약          │
  │                                                                                       │
  └───────────────────────────────────────────────────────────────────────────────────────┘
                                          │
                                          ▼
  ┌─────────── user prompt (per-call, 캐시 안 됨) ───────────┐
  │                                                          │
  │   DATE: 2026-05-22                                       │
  │   NEW NOTE (daily/2026-05-22):                           │
  │     <신규 block 들만>                                  │
  │                                                          │
  └──────────────────────────────────────────────────────────┘
                                          │
                                          ▼
                          Haiku → submit_ingest_result tool call

  Tier 3 (read_page / search_wiki tools) — 코드에는 있으나 ingest에서는 enableTools: false 로 OFF.

왜 분리? 시스템 프롬프트는 크지만 안정적, user prompt는 작고 매번 다름. Anthropic prompt cache 5분 TTL 안에 반복 호출하면 ~90% 비용 절감.

5. 비판 — 미완·비효율·사족

이 섹션은 "지금 이대로 운영하면 어디가 아플까"의 솔직한 진단. 우선순위 순.

5.1 미완 (Karpathy 패턴이 요구하는데 우리에게 없음)

① Query 동작 부재

코드 검색 결과: /ask, wikiQueryMode 없음. docs/llm-wiki-redesign-plan.md §3.2에 "⏳"

위키 누적의 가치를 닫는 양방향 루프 (질문 → 답 → 새 사실 환류) 없음. 일반 chat은 있지만 "내 위키 기반 + 출처 표시 + 새 발견 환류"는 미구현. 대화에 들어간 정보가 위키로 흘러들어오지 않음 — 누적 채널의 한쪽 절반이 비어 있음.

참고: docs/wiki-explainer.html 230~340줄에 "흐름 3: /ask"가 있지만 실제 구현 없음. 문서가 코드를 앞서감.

② Lint 동작 부재

검색 결과 없음. llm-wiki-redesign-plan.md §3.3에 "⏳"

모순(같은 사실 다르게 적힘), stale, orphan, 지식 공백 자동 탐지 없음. 위키가 자라면 결국 부패 — Karpathy도 "Lint는 위키가 100페이지를 넘는 순간 필수"라고 명시. 지금은 사용자가 직접 찾아내야 함.

5.2 비효율 (있긴 있는데 무겁거나 중복)

③ Tier 3 도구 절반만 연결

agent/contextPipeline.ts:33 DEFAULT_TOOLS = ['read_page', 'search_wiki']

코드에 도구 이름은 있고 sidecar에 등록도 돼 있지만, ingest는 enableTools: false로 끔. 즉 LLM이 필요한 페이지를 능동적으로 가져올 수 없음. 결과: Tier 2의 [[link]] 휴리스틱에만 의존. 위키 페이지가 적을 땐 OK, 많아지면 LLM이 "이 fact는 [Project Z] 페이지에 있을 텐데" 라고 인지해도 닿을 수 없음. 도구 이름만 import해두고 실제 비활성 → 절반 구현.

④ proof-sdk 우회 자체구현 4건 — 표면 버그 근원

docs/wiki-arc-roadmap.md Arc 1~4

같은 저장소에 proof-sdk가 이미 푼 4가지 기능을 자체 구현으로 우회하고 있음 (semantic anchoring, /ops endpoint, 3축 provenance, agent bridge). 표면 버그들 (위키 본문에 헤더 중복 박힘, "서버가 가끔 마크 되돌림", AI attribution 드리프트)이 모두 여기서 나옴. Arc 1은 완료, Arc 2~4 진행 중.

⑤ aiSummary 생성을 위한 별도 LLM 호출

state/wikiService.ts:306 regenerateAiSummaryForSlug(slug)

새 wiki 페이지 만들 때 fire-and-forget으로 LLM 호출 추가 → sidecar .meta.json의 aiSummary 채움. Index 라인의 summary 컬럼용. 안 채워지면 본문 둘째 줄로 폴백되니 정확성 영향은 없지만, 매 신규 페이지마다 LLM 호출 1회 추가. Karpathy 원본은 본문 첫줄 = title, 둘째 = summary 규약으로 LLM 호출 없이 처리.

⑥ 3중 dedup — block-hash + watermark + LLM 판단

ingest/index.ts:185, useIdleTrigger.ts, prompts.ts (자체 invariants)

(a) block-hash로 새 block만 추출 + (b) lastEditedAt > lastIngestedAt watermark gate + (c) 프롬프트에 "이미 INDEX에 있으면 skip" 룰. 셋이 같은 일을 다른 층에서 함. 안전하긴 한데, (b)가 (a)와 사실상 중복 (b가 통과하면 (a)가 또 거름). (b) 폐기 가능 후보.

5.3 사족 (Karpathy 본 코드에 없는 추가 — 진짜 필요한가?)

⑦ wiki:profile 페이지의 zone 룰

state/wikiService.ts:88~95 (DEFAULT_CONVENTIONS), prompts.ts §"Routing self-facts to wiki:profile"

## Voice / ## Themes / ## About / ## Sources / ## Background / ## Notes — 6개 섹션마다 다른 ownership 규칙. ingest는 ## Background에만 append. 시스템 프롬프트에 이 룰 설명을 매번 박음. Karpathy의 평면 페이지 원칙 (하나의 엔티티 = 하나의 페이지, flat list of bullets) 과 어긋남. profile 페이지 하나 때문에 프롬프트 분기 + 컨벤션 분기 + 적용 분기가 추가됨. URL 분석 파이프라인이 이 페이지에 의존하니 빼긴 어렵지만, 복잡도 비용은 인지해야 함.

⑧ 채팅 활동 블록을 ingest 컨텍스트에 끼움

prompts.ts L146 + selectActiveThreadsForIngest.ts + compactChatThread.ts

지난 ingest 이후 사용자가 했던 채팅 thread들을 entity: fact bullet으로 compact해 시스템 프롬프트 끝에 넣음. Karpathy 원본은 "source가 곧 인풋" — daily 하나. 우리는 daily + 채팅 두 소스. 의도는 좋지만 compact 단계에서 thread당 LLM 호출 1회 추가 (stale thread 요약용). ingest 1회당 LLM 호출이 1 + N (active threads). 채팅이 많은 날 비용 급증.

⑨ system page의 lazy create 패턴 — 4번 반복

state/wikiService.ts ensureLogWikiSlug / ensureConventionsWikiSlug / ensureIndexWikiSlug / ensureProfileWikiSlug

이미 SystemPageConfig로 추출됐고 helper도 한 줄짜리라 부채는 작음. 다만 callsite마다 "쓰기 전에 ensure" 패턴을 박는 게 비싸짐. bootstrap 한 군데서 미리 4개 다 만들면 ingest / chat / index persist의 ensure 호출이 다 빠짐. lazy의 가치는 "쓰지도 않을 페이지 안 만든다"인데, 4개 다 거의 항상 쓰임 → lazy가 사족.

⑩ AuthoredMeta sidecar (Y.Map) — proof-sdk 3축 provenance 우회

hooks/useCollabDoc.ts:110~124

마크 attr에 직접 origin/basis/review 박는 SDK 표준 대신 별도 Y.Map('authoredMeta')에 sourceSlug/Label/Quote만 저장. 동기화 비용 + 마크와 사이드카 정합성 깨질 여지 + 서버 projection이 인식 못 함. Arc 4에서 폐기 예정.

6. 한눈 요약

  • Index = 모든 위키 페이지의 한 줄 카탈로그. LLM이 안 쓴다 — 시스템이 결정적으로 빌드한다. buildWikiIndex()가 knownDocs + sidecar + backlink count로 매번 같은 결과 생성. 200ms debounce로 디스크 persist.
  • 위키 생성 = daily 본문에서 새 block 추출 → 컨텍스트 4종 (rules / index / hot pages / self profile / 채팅 활동) 조립 → Haiku가 submit_ingest_result 툴로 proposal 반환 → 큐에 쌓임 → 사용자가 해당 wiki 페이지 열면 banner에서 ✓/✕ → accept면 페이지 끝에 append + index 무효화 → 200ms 후 index 재빌드.
  • 미완: Query (/ask), Lint. 둘 다 Karpathy 패턴의 핵심.
  • 비효율: Tier 3 도구는 import만 하고 OFF. proof-sdk가 푼 4개 문제를 자체 구현으로 우회. aiSummary용 추가 LLM 호출. dedup 3중첩.
  • 사족: wiki:profile zone 룰 (Karpathy의 flat 원칙 위반). 채팅 활동 ingest (LLM 호출 N+1). 4개의 lazy-create (사실상 항상 쓰임).
