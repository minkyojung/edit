# 옵시디언 유저 피기배킹 GTM & 온보딩 전략

> AI-native 노트앱(manila / writer-tauri)으로 옵시디언 유저를 데려오기 위한 제품·그로스 전략.
> 핵심 원칙: **마이그레이션시키지 말고, 기존 vault 위에 올라타라.**

---

## 0. 핵심 통찰 (한 줄)

옵시디언 유저를 데려오는 가장 효율적인 피기배킹은 그들을 옮기게 만드는 게 아니라,
**그들의 기존 vault 위에 그대로 올라타는 것.** 이주 결정 자체를 없앤다.

---

## 1. 문제의 재정의: 왜 "가져오기(import)"가 함정인가

옵시디언 유저의 선택 이유가 곧 이탈 저항의 정체다.

- 그들은 **로컬 우선 + 평문 마크다운 + 데이터 소유권** 때문에 옵시디언을 골랐다 → 락인 공포.
- 수천 개 `.md` 파일, `[[위키링크]]`, frontmatter, 플러그인 워크플로우를 수년간 축적.
- "우리 앱으로 import 하세요"는 **그들이 옵시디언을 고른 바로 그 이유(락인 회피)를 정면으로 자극** → 전환율 구조적 하락.

→ 결론: **이주 결정 자체를 없애야 한다.** 결정을 요구하는 순간 대부분 이탈한다.

## 2. 전략 옵션 비교

| 옵션 | 내용 | 평가 |
|---|---|---|
| **A. 전체 마이그레이션** | export → import, 우리가 저장소 통제 | 가장 직관적이지만 락인 공포 직격, 올오어낫싱, 워크플로우 파괴 → **전환율 최악** |
| **B. Vault-on-top** ⭐ | 기존 vault 폴더를 그대로 읽고 쓴다. 옵시디언과 동시 사용(dual-run). AI/메모리는 사이드카 | 마이그레이션 위험 0, 가역적, 신뢰 우선. 대가: 마크다운 라운드트립 충실도 엔지니어링 |
| **C. 옵시디언 플러그인** | 유저가 이미 있는 곳에 침투 | 시도 마찰 최저, 하지만 남의 집 손님 → **획득 채널로만** 사용 |

**판정: B를 본체로, C를 획득 채널로.** 둘은 경쟁이 아니라 퍼널의 다른 층.

---

## 3. 추천안: "Vault-on-top + 사이드카 메모리 + 플러그인 비치헤드"

### 가장 효과 좋은 단일 레버: **가역성(reversibility)**

> 같은 마크다운 파일에 되써주기 때문에, 유저는 "전환하겠다"는 결정을 한 번도 내릴 필요가 없다.
> 그냥 우리 앱을 vault에 연결해 열어볼 뿐이고, 옵시디언은 그대로 백업으로 남는다.

커밋을 요구하지 않으니 활성화 마찰이 거의 0. 시간이 지나며 AI 레이어가 우리 앱에만 있으니
**일상 사용이 조용히 우리 쪽으로 이동** → 옵시디언이 점점 "백업 폴더"가 된다.

### 세 층의 역할 분담

| 층 | 위치 | 역할 |
|---|---|---|
| **소스 오브 트루스** | 유저의 평문 `.md` vault | 절대 오염 안 함. 옵시디언과 공유. "당신 파일은 당신 것" 약속 유지 |
| **메모리/인덱스** | 사이드카 (`.manila/` or 별도 DB) | 임베딩·시맨틱 인덱스·대화 메모리. 우리의 해자 |
| **AI 경험** | 네이티브 앱 (이 Tauri 앱) | 옵시디언이 못 하는 것. 일상 사용을 끌어오는 자석 |

---

## 4. 그로스 메커니즘: 왜 효율적인 피기배킹인가

### 퍼널 (신뢰 사다리)

1. **획득** — 옵시디언 커뮤니티에서 만난다 (r/ObsidianMD, Discord, 플러그인 디렉토리).
   메시지: *"마이그레이션 없음. 당신 vault를 그대로 읽고 AI를 얹습니다."*
2. **활성화** — 폴더 가리키기 30초 (vs 마이그레이션 수 시간). **기본은 읽기 전용** → 위험 0.
3. **유지** — vault 전체를 읽기에 가능한 AI 메모리. *옵시디언이 native로 못 주는 것.*
4. **전환** — AI가 우리 앱에만 살기에 일상이 이동. 옵시디언은 백업으로 강등.

### 왜 CAC가 낮은가

- 옵시디언 유저는 기술적·목소리 큼·커뮤니티 중심 → "락인 없이 AI 얹어줌"은 공유되기 좋은 신뢰 메시지.
- 폴더 연결 = 즉시 활성화. 데모 한 개로 "내 진짜 vault에서 바로 도는" 걸 증명.
- 플러그인 비치헤드로 무료 시드 기능(vault-AI 검색) 배포 → 네이티브 앱으로 업셀.

### 과금 경계

읽기 전용 vault 연결 + 기본 검색은 **무료**. AI 메모리(전체 인덱스·대화·자동 연결)는 **유료**. Land-and-expand.

## 5. 온보딩 설계

### 5.1 다양성은 두 개의 축으로 나뉜다

케이스가 많아 보이는 이유는 **데이터 상태**와 **유저 의도**를 섞어 보기 때문. 분리하면 정리된다.

**축 A — Vault 데이터 상태**

| 케이스 | 위험/난점 |
|---|---|
| 빈손 (옵시디언 미사용) | vault 없음 → 새로 시작 경로 |
| 작고 깔끔한 vault | 가장 쉬움. 기준선 |
| 거대 vault (수천~수만) | 인덱싱 시간·성능·메모리 |
| 플러그인 헤비 (Dataview/Templater) | **우리가 못 읽는 비표준 문법** |
| 이미 동기화 중 (iCloud/Sync/git) | **우리가 쓰면 충돌** |
| 첨부·미디어 헤비 | 큰 바이너리, canvas/excalidraw |

**축 B — 유저 의도/심리**

| 유형 | 핵심 니즈 |
|---|---|
| **평가자** ("안 버리고 그냥 써볼래") | 가역성·읽기 전용 — **가장 큰 세그먼트** |
| **병행자** ("영구히 둘 다") | 충돌 안전성 |
| **이주 결심자** ("옮길래") | 소수, 고가치 |
| **백업 불안형** | 신뢰 증거 |

### 5.2 핵심 통찰: 케이스를 경로로 만들지 말고, 기본값으로 흡수하라

> **"읽기 전용으로 vault 가리키기"는 위 모든 케이스에서 안전하다.**

거대하든, 플러그인 헤비든, 동기화 중이든 — 읽기만 하면 아무것도 안 망가진다.
모든 유저를 이 단 하나의 첫 행동으로 수렴시키고, 위험한 결정(쓰기·전환)은 전부 뒤로 미룬다.
이게 "단순하면서 포용적"의 유일한 구현 방식.

### 5.3 추천 온보딩 구조 — 4스텝, 분기는 단 1개

```
1. 연결(Connect)   ← 유일한 분기
     ├─ "기존 vault 폴더 선택"   (옵시디언 유저)
     └─ "새로 시작"              (빈손)

2. 이해(Index)     읽기 전용 인덱싱. 진행률 + "못 읽은 것" 투명 표시

3. 아하(Aha)       vault 전체를 아는 AI 질의 1회 → 즉시 가치

4. (선택) 쓰기 활성화   명시적 옵트인 + 자동 스냅샷 백업
```

- **분기는 step 1의 2갈래뿐.** 나머지 다양성은 모두 기본 경로가 적응으로 처리.
- step 4 전까지는 **위험 0** → 평가자/불안형/병행자가 부담 없이 통과.
- step 3에서 "옵시디언 검색이 못 찾는 의미적 연결"을 한 번 보여주는 게 활성화의 급소.

### 5.4 다양성을 "케이스"가 아니라 "적응"으로 처리

| 데이터 상태 | 적응 방식 (분기 아님) |
|---|---|
| 거대 vault | 점진적·백그라운드 인덱싱. 일부만 돼도 즉시 사용 가능 |
| 못 읽는 플러그인 문법 | **원문 그대로 보존(pass-through)**, "이 블록은 원문 유지" 표시 |
| 이미 동기화 중 | 감지 → 경고 → **읽기 전용 권장**, 쓰기는 더 강한 확인 |
| 깨진/실패 파일 | 한 파일 실패가 전체를 막지 않음. 건너뛰고 목록화 |
| 빈손 | step 1에서 "새로 시작" → 샘플/템플릿 |

포용성의 진짜 핵심은 **"못 읽는 것을 숨기지 않는 투명성"**.
Dataview를 못 렌더해도 그 블록을 손대지 않고 그대로 두고 "원문 보존"이라 알리면 유저는 안전하다고 느낀다.
침묵하거나 임의 변환하는 순간 신뢰가 깨진다.

## 6. "안전하게 가져오기" = 라운드트립 충실도 (제품의 생사)

"에러 전혀 없는 Wellmade" 요구가 여기에 직결. **단 한 번의 파일 손상이 전체 GTM을 죽인다.**

엔지니어링 불변식:

- **절대 파괴적 재작성 금지.** frontmatter 키 순서·공백·들여쓰기까지 보존.
  (Milkdown은 ProseMirror/remark 기반 → 옵시디언 비표준 문법과의 라운드트립이 최대 기술 리스크)
- 쓰기 전 **스냅샷/git 백업** 자동.
- **읽기 전용이 기본**, 쓰기는 명시적 옵트인.
- 옵시디언 고유 문법 완전 대응: `[[wikilink]]`, `![[embed]]`, `#tag`, callout, 블록 참조 `^id`, alias.
- **Dual-run 충돌 처리** — 옵시디언과 우리 앱이 동시에 같은 파일을 열었을 때.

이건 단순 기능이 아니라 **약속의 증거**. "당신 파일을 안 망친다"를 코드로 증명 못 하면 메시지 전체가 무너진다.

## 7. 메모리 레이어 = 차별점이자 해자

- vault 전체를 인덱싱 → 임베딩/시맨틱 메모리 → 전 지식베이스를 아는 AI.
- **단, 메모리는 사이드카에 저장하고 `.md`를 오염시키지 않는다.** 소스는 깨끗·이식 가능하게 유지.

### 정직한 트레이드오프

> 우리의 해자(메모리/인덱스)는 사이드카에 쌓이고 **이식되지 않는다.**
> 즉 전환 비용은 그들의 *원본 파일*이 아니라 *우리가 파생시킨 메모리 층*에 누적된다.
> 데이터를 인질로 잡는 게 아니라 **파생 가치로 묶는다.** 윤리적·마케팅적으로 방어 가능한 유일한 해자 위치.

## 8. 놓치면 신뢰가 무너지는 엣지 케이스

- **이미 동기화 중인 vault** — iCloud/Obsidian Sync/git과 동시 쓰기 충돌. 감지·경고 필수.
- **엉뚱한 폴더 선택** — vault 루트 오인식 방지 (`.obsidian` 존재로 vault 인식).
- **macOS 폴더 접근 권한** — Tauri 권한 prompt를 온보딩에 자연스럽게 녹이기.
- **읽기 실패 graceful** — 한 파일이 전체 인덱싱을 막으면 안 됨.
- **첫 쓰기의 무손상 증명** — 백업 + 라운드트립 보장이 step 4의 전제.

---

## 9. 리스크 (정직하게)

- **마크다운 충실도** — Milkdown↔옵시디언 라운드트립이 1순위 기술 리스크이자 신뢰 약속의 급소.
- **Dual-run 파일 충돌.**
- **타이밍** — 옵시디언이 native AI를 강화 중. 비치헤드를 빨리 박아야 함.
- **사이드카 해자의 한계** — 충분히 강력한 AI 경험이 없으면 "그냥 옵시디언 + 무료 플러그인"에 밀림.

## 10. 실행 로드맵 (이 Tauri 앱 기준, 검증 가능하게)

```
1. Vault 어댑터: 폴더 가리키기 + 읽기 전용 인덱싱
   → verify: 실제 옵시디언 vault 1000+ 파일 무손상 파싱, [[링크]]/frontmatter 보존
2. 라운드트립 쓰기 + 스냅샷 백업 (옵트인)
   → verify: 100개 파일 열고-저장 후 git diff = 빈 diff (바이트 동일)
3. 사이드카 메모리: vault 전체 임베딩 + 채팅 메모리
   → verify: "내 vault에서 X 관련 노트" 질의가 옵시디언 검색이 못 찾는 의미적 연결 반환
4. 플러그인 비치헤드: 옵시디언 안에서 무료 vault-AI 검색 → 네이티브 앱 업셀
   → verify: 플러그인 설치→앱 활성화 전환율 측정
```

## 한 줄 요약

**마이그레이션을 팔지 말고 "락인 없는 AI 레이어"를 팔아라.**
기존 vault에 100% 충실도로 올라타 가역성으로 결정 부담을 없애고(=피기배킹 엔진),
AI 메모리는 파일을 건드리지 않는 사이드카에 쌓아 해자를 만든다.
단일 최강 레버는 **"내 진짜 vault에서 위험 0으로 바로 돌아가는" 30초 활성화 경험**.

온보딩은 케이스를 세지 말고 분기를 세라 — 진짜 필요한 분기는 "기존 vault냐 / 새로 시작이냐" 단 하나.
