## 2. 전략 논지의 정밀화 (중요한 교정 1개)

사용자 논지: "CM이 더 컴퓨터/AI 친화적이고, AI에게 더 **디테일한 정보**를 줄 수 있다."

**방향은 옳지만 이유를 정확히 해야 한다:**

- ✅ 맞는 부분 — **네이티브 표현(native representation)**: LLM은 텍스트/마크다운/diff로
  학습·추론한다. CM의 문서가 곧 마크다운이라, 모델이 보는 표현과 에디터의 진실이
  **동일**하다. 좌표도 모델이 잘 다루는 char offset/line. PM은 트리(스키마)라 모델의
  텍스트 좌표를 트리 위치로 **번역**해야 하고(우리가 측정한 그 ~900 LOC), 번역마다
  드리프트/버그 여지가 생긴다.
- ⚠️ 교정 — "더 디테일/구조적"은 사실 PM이 더 그렇다(트리가 텍스트보다 구조 정보가
  많다). CM의 진짜 우위는 **"정보의 양"이 아니라 "정보가 모델의 모국어(텍스트·offset·
  diff)로 표현된다"**는 점. 그래서 손실·번역비용·툴 마찰이 작다.
- ✅ "디테일한 정보"가 옳은 또 다른 의미 — **상호작용/편집 스트림**: CM의 ChangeSet은
  1급 시민인 **직렬화·재베이스 가능한 편집 로그**다. 커서·선택·뷰포트·"방금 무엇이
  어떻게 바뀜"을 전부 텍스트 좌표로 싸게 모델에 줄 수 있다. **실시간 프로액티브 협업
  (페어코딩식)**의 이상적 기반 — 이 의미에선 사용자의 "더 디테일한 정보" 직관이 정확.

## 3. 다관점 검증 — 동의 vs 반박

### (A) 에디터/시스템 엔지니어 (리치텍스트 에디터 구축 경험자)
- 동의: 문서가 **마크다운 중심**이면 PM은 과설계. Obsidian(CM) vs Notion(트리)의 갈림길에서
  우리는 마크다운-온-디스크 → CM 진영이 맞다.
- 반박/주의: 트리 모델은 **구조적 복잡도**(중첩표·각주·트랜스클루전·제자리 편집 리치객체)
  에서 값을 한다. text+데코는 90%를 주지만 마지막 10%가 "모래성"이 될 수 있다. 또한
  **undo/redo·IME·접근성·모바일·위젯 넘나드는 선택**은 PM이 수년간 다진 영역 — CM 재구현이
  그 버그들을 다시 만난다(재구현 비용의 실체).

### (B) AI/에이전트 엔지니어 (LLM 코딩 에이전트·tool-use 구축)
- 강하게 동의: 에이전트 편집 툴체인(apply_patch/unified diff/search-replace, 라인범위,
  LSP)은 **전부 텍스트+offset 전제**. CM은 이 세계관을 그대로 상속, PM은 별도 레이어를
  덧대야 한다. ChangeSet 재베이스 = 사용자/모델 동시편집 충돌 해소가 내장.
- 주의(사용자가 놓친 부분): "더 많은 텍스트를 context에"가 미덕은 아니다 — 토큰 비용.
  진짜 이득은 **충실도와 툴 ergonomics**이지 raw 양이 아니다. 그리고 **"AI가 큰 문서를
  이해"의 병목은 에디터가 아니라 검색/구조/청킹/프롬프트**다(아래 §5).
- 추가 뉘앙스: PM의 의미적 step("체크리스트로 변환")이 어떤 경우 텍스트보다 **고신호**일
  수 있다. 즉 텍스트가 절대적으로 더 정보적인 건 아니고, **더 보편적·저마찰**인 것.

### (C) Anthropic식 리서처 (context window·tool 설계·신뢰성·bitter lesson)
- 동의: 모델은 인터넷(텍스트·코드·마크다운)으로 학습 → **산출물과 학습분포의 간극을
  최소화**하라. 마크다운=in-distribution, PM JSON/트리경로 주소지정=out-of-distribution·
  brittle. 좋은 에이전트 툴은 단순한 text-in/out + 안정적 주소지정(str_replace 류) — CM이
  1:1로 맞는다. "Reliable, 에러 없는 제품" 요구도 번역 레이어 제거(왕복버그 0)와 정합.
- 반박/엄격성: **네이티브 표현은 양날**이다. 제품이 리치 구조(시각화 엔진·카드)를 요구하면,
  텍스트 위에 별도 렌더 레이어를 유지하게 되고 **모델이 텍스트를 망가뜨려 위젯 불변식을
  깰 수** 있다(스키마가 강제하던 유효성이 사라짐). 즉 "serialize 드리프트 버그"를
  "유효성 드리프트 버그(모델이 깨진 mermaid/HTML 생성)"와 맞바꾸는 면이 있다 — 순효과는
  여전히 CM 우세일 수 있으나 공짜는 아니다. 그리고 이 모든 논의를 **경험으로 검증**하라고
  요구할 것 — 우리는 이미 측정했다(5.5×, 100%). 그래서 결론이 "서사"가 아니라 "증거"에
  선다.

## 4. 합의 / 불일치 요약

- **세 관점 모두 동의**: 마크다운-온-디스크 + AI가 실시간 편집하는 제품이라면, 텍스트
  네이티브(CM)가 에이전트 친화·신뢰성·툴 정합에서 우위. AI 협업 축은 명백히 CM.
- **불일치 지점**: "리치/구조적 편집"의 비중. 비중이 크면 트리(PM)가 값을 한다. → 그러나
  우리 전제(WYSIWYG·카드는 부수적)와 실측(카드/차트가 CM 위젯으로 성립)이 이 반대를
  대부분 무력화.
- **모두가 거는 단서**: ①유효성 드리프트(모델이 깨진 임베드 생성) ②성숙한 에디터 동작
  (IME/undo/a11y/모바일) 재구현 비용 ③에디터 선택은 "큰 문서 이해"를 풀지 않음(§5).

## 5. 자주 헷갈리는 점 — "문서가 커지면 AI가 직관적으로 이해"

에디터 모델(CM vs PM)은 **AI가 큰 문서를 이해하는지와는 거의 무관**하다. 두 경우 모두
모델에는 마크다운을 준다. 큰 문서 이해를 좌우하는 것은: **문서 구조(제목/섹션), 안정적
주소지정, 청킹/검색(RAG), 프롬프트 설계**. CM이 기여하는 곳은 **정확·안정·네이티브한
주소지정 + 편집 충실도**이지 "이해력 자체"가 아니다. → 큰 문서 대응은 CM 위에서 **구조화/
검색 레이어를 따로** 설계해야 하는 별개 과제(이주와 독립).

## 6. 결론 / 권고

- **판정: 우리 제품 전제 하에서 CM 이주는 정당.** AI 협업(핵심)·WYSIWYG·카드 세 축 모두
  실측으로 청신호이고, 사용자의 전략 직관(텍스트 네이티브 = AI 친화)은 AI/에이전트·
  리서처 관점과 일치한다 — 단 "더 디테일"이 아니라 "**모델의 모국어로 표현**"이 정확한 이유.
- **단, 결정이 아니라 단계적 전환을 권고**(되돌리기 어려운 문):
  1. 이미지·미디어 카드까지 CM 위젯 구현(쉬움) → 카드 축 마감.
  2. **~20개 PM 플러그인 + 편집 동작(들여쓰기 단축키 등) 이주 범위·공수 산정**(코딩 전 문서).
  3. **유효성 드리프트 가드**(모델이 깨진 임베드 생성 시 폴백·검증) 설계 — §3(C) 리스크.
  4. 성숙한 에디터 동작(undo/IME/a11y/모바일) 회귀 테스트 셋업.
  5. 그 위에서 "큰 문서 이해"용 구조/검색 레이어(별개 트랙) 설계.
- **하지 말 것**: 서사에 취해 한 번에 전환. 우리 강점은 "측정했다"는 것 — 단계마다 같은
  방식(숫자+눈)으로 검증하며 간다.

## 9. 전면 이주 실행 로드맵 (단계별)

프로토타입은 "되는가"를 증명했고, 실제 이주는 이걸 **프로덕션 에디터로 승격**하는 일.

1. **에디터 셸 교체** — MilkdownEditor → CM EditorView를 실제 문서 로드/저장 경로
   (docsStore.bodyMarkdown ↔ doc)에 연결. parser/serializer 제거(doc=마크다운).
2. **AI 협업 배선** — 검증된 offset 앵커층을 `pendingChangesStore`에 연결(이미 store는
   에디터 무관). proof 마크 = 데코.
3. **기능 이식** — 프로토타입 모듈(livePreview/카드/슬래시/위키링크/서식/링크/하이라이트/
   미디어/상태)을 프로덕션 품질로 승격 + 실제 스토어/볼트/라우터에 연결(토스트 → 실제 동작).
4. **데일리 가드 등 도메인 규칙** 이식(에디터 무관 로직).
5. **안전장치**: 유효성 드리프트 가드(모델이 깨진 임베드 생성 시 폴백/검증),
   undo/IME/접근성/모바일 회귀 테스트.
6. **마감(cosmetic)**: 슬래시 아이콘(@tabler), 팝업/엣지/드롭커서 색 토큰, 번호 리스트
   재넘버링, 링크 호버 바.
7. **(별개 트랙)** "큰 문서 이해"용 구조/검색 레이어 — 에디터와 독립.

> 권고: 한 번에 스위치하지 말고 **기능별 플래그/병행**으로 승격, 단계마다 숫자+눈 검증.

## 10. 미해결/주의 (이주 실행 시)

- **유효성 드리프트**: 스키마가 강제하던 유효성이 사라짐 → 모델이 깨진 mermaid/HTML
  생성 시 폴백·검증 필요(이미 카드 위젯이 폴백 렌더는 함).
- **성숙한 에디터 동작**: IME/undo/접근성/모바일은 PM이 다진 영역 — 회귀 셋업 필수.

- **선택 툴바**: 비마크다운 사용자 발견성 떨어지면 additive로 재도입 가능(지금 스킵).

## 11. 부록 — AI 편집 정밀성·신뢰성 실증 (2026-06-10)

§7의 프로토타입은 "에디터가 CM에서 성립하는가"(렌더링·편집 손맛)를 증명했다. 이번
라운드는 그보다 **PoC의 진짜 논제** — *"CM의 풍부한 데이터로 AI가 더 정교하고 안전하게
텍스트를 수정한다"* — 를 직접 데모로 닫았다. 스파이크는 `src/prototypes/v2/`, DEV 라우트.

### 11.1 출발점 교정 — 현 제품의 실제 AI 편집 경로

조사 결과(메인 제품): AI는 MCP 툴 `propose_edit`/`propose_multi_edit`/`propose_write`로
**`old_string → new_string`(텍스트 쌍)** 만 보낸다. 앵커링은 위치도 Yjs도 아닌
**텍스트 검색**(`lib/looseMatch` 2단계: 정확→마커제거 정규화, **중복이면 ambiguous→
null로 포기**). AI가 받는 컨텍스트는 **풀 문서 텍스트(60k 잘림)뿐 — 선택/커서/구조 없음**.
수락은 `pendingChangesStore`(runId 배치)→flush→`ai-edit:` 커밋, 실패 시 reopen+토스트.

**함의**: 현 제품은 CM의 강점(정확 위치·구문 트리)을 **전혀 쓰고 있지 않다**. 따라서
이주 정당성은 "AI 편집이 실제로 더 나아진다"로 증명되어야 하며, 이번 라운드가 그것이다.

### 11.2 실증 1 — 구조 기반 정밀 앵커 (`#/dev/proofanchor`)

같은 입력(`old_string→new_string`)을 두 방식으로 해소해 나란히 비교:

| | 제품(텍스트 검색) | CM(구문 트리) |
|---|---|---|
| 중복 단어 | 매치 ≥2 → **ambiguous, 포기(편집 실패)** | 모든 occurrence를 **정확 범위 + 구조 라벨**로 해소 |
| 모호성 해소 | 불가 | "표 셀 안의 그것" 등 **구조로 정확히 1개 지정** |
| AI 컨텍스트 | 없음 | 각 위치의 구조 라벨을 **AI에 돌려줄 수 있음** |

- 모듈: `anchorResolve.ts` — `structuralContext()`(구문 트리를 거슬러 가장 구체적
  컨테이너 선택; list item이 그 안 paragraph를 이김), `resolveAnchors()`(모든
  occurrence에 라벨), `naiveMatch()`(제품의 "중복이면 포기" 재현, 대조군). 테스트 5/5.
- **결론**: 제품이 포기하는 입력을 CM은 구조로 정확 처리. 이주 정당화의 핵심 증거.

### 11.3 실증 2 — 제안 생명주기·신뢰성 (`#/dev/anchorlife`)

"에러 전혀 없어야"라는 제품 기준에 맞춘 **precision-or-abstain**(정확히 못 붙이면 틀리게
넣지 말고 비워서 보여줌) 정책을 3상태로 구현:

- **살아있음(alive)**: 열려 있는 동안 위치는 `ChangeSet.mapPos`로 **정확 추적**(재검색 0,
  드리프트 0). 본문 인라인 렌더.
- **낡음(stale)**: 사용자가 제안 범위 안쪽을 직접 고쳐 따옴표가 더는 안 맞음 → 흐리게 +
  "원문 바뀜", **자동 적용 차단**.
- **미배치(unplaced)**: 따옴표를 못 찾음/범위 붕괴 → 트레이에 표시, **절대 오배치 안 함**.
- **다시 열기(reload)**: 위치는 휘발 → `{quote, context}`로 재anchor(11.2 재활용).
  유일=재발견, 중복=**구조로 가려냄**, 소멸=미배치. 마크다운 본문은 깨끗(사이드카 모델).
- 모듈: `anchorLifecycle.ts`(`liveSugField` 위치매핑, `sugState`, `reanchor`). 테스트 4/4.

### 11.4 실증 3 — 손맛 잔여 버그 근본 수정 (블록 위젯 수직 이동)

`blockVerticalNav.ts`: 표·이미지·미리보기 타일 등 **키 큰 블록 위젯이 연달아 쌓인 곳**을
화살표로 가로지를 때 CM의 화면-픽셀 수직 스캔이 폭주(여러 줄 점프)하던 문제. **CM 결과를
먼저 보고, 인접 줄로 잘 가면 그대로 두고(정상 경로 무손상), 폭주했을 때만** 인접 raw 줄로
교정. 표 진입은 `tableArrowEntry`가 계속 담당. 계측(로그)으로 원인 확정 후 수정 → 제거.

### 11.5 정밀화된 AI-협업 이주 로드맵

§9 로드맵의 "AI 협업 배선" 단계를 이번 실증으로 구체화. 검증된 모듈이 그대로 프로덕션
씨앗이 된다:

| 단계 | 내용 | 씨앗(검증됨) |
|---|---|---|
| **A. 앵커 해소** | `old_string`을 구문 트리로 해소, 중복은 구조로 disambiguate | `anchorResolve.ts` |
| **B. 생명주기·상태** | alive/stale/unplaced + 다시 열기 재anchor, precision-or-abstain | `anchorLifecycle.ts` |
| **C. 렌더·추적** | 제안 = 데코(취소선/교체/위젯), 정확 추적 | `proofMarks.ts` |
| **D. 스토어 연결** | 위 A~C를 **기존 `pendingChangesStore`(에디터 무관)** 에 배선. 사이드카 영속(quote/context/kind/occurrence) | (제품 store 재사용) |
| **E. 다중 제안** | 한 런(runId)의 여러 edit 공존 + 그룹 수락/거절 | (미구현 — ②) |
| **F. 마크 타입** | comment·delete(취소선)·highlight 등 5종 확장 | suggestion(교체/삽입)만 됨 — ③ |
| **G. 구조 컨텍스트 상향** | AI에게 선택/커서/구조 라벨을 제공 → AI가 "표 2행의 그것"처럼 지정 | 11.2가 반환값까지 준비, 프롬프트 배선 미구현 |
| **H. 패리티** | vizId 시각화·슬래시·위키링크·미디어 카드 등 §9 기능 이식 | §7 모듈 |

### 11.6 미해결/주의 (이번 라운드 기준 갱신)

- **②다중 제안·③마크타입·G구조컨텍스트**: PoC 판정엔 비필수(핵심 논제는 ①④로 증명),
  구현 단계의 본 작업. 특히 **G(AI에 구조 제공)** 가 11.2의 잠재력을 실제 제품 이득으로
  바꾸는 핵심 — 프롬프트/툴 스키마에 구조 컨텍스트를 넣는 일.
- **사이드카 영속 포맷**: 제안을 `{id, quote, after, kind, context, occurrenceIndex,
  status, createdAt}`로 저장. 본문 .md는 깨끗 유지(제품 기존 결정과 동일).
- **재진입 경계 케이스**: 같은 구조 컨텍스트 안에서도 중복이면 occurrenceIndex 폴백 필요.

### 11.7 판정 (갱신)

§8의 **GO(조건부)** 유지·강화. 이번 라운드로 "왜 CM인가"가 코드량(§7, ~5.5×)뿐 아니라
**AI 편집의 정밀성(①)·신뢰성(④)** 으로도 데모 증명됨. 남은 것은 리스크가 아니라 **분량
(E~H)** 이며, 모두 검증된 씨앗 모듈에서 출발한다.
